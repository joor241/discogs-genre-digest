Digest settings

Add or remove stores, edit the genre filter, and trigger a run — without touching code.

Fastest way — no token needed

You're already signed in to GitHub in your normal browser, so editing values there is quicker than setting up a token here. Use this unless you specifically want the nicer editor and live store-checking below.

First link opens the Variables list — click a name (e.g. GENRES_INCLUDE) to edit its value inline. Second link opens a one-off "Run workflow" form for trying different genres or a longer lookback without changing anything permanently.

Connect

Editing lives on GitHub, so this page needs a token to read and write your repository's settings on your behalf. It is sent straight from your browser to api.github.com and nowhere else, and is never seen by anyone building or maintaining this page.

How to get a token (one-time, ~1 minute)
  1. Open github.com/settings/personal-access-tokens/new (sign in if asked).
  2. Under Repository access, choose Only select repositories and pick discogs-genre-digest.
  3. Under Permissions → Repository permissions, set Variables to Read and write, Actions to Read and write (the second one lets "Save & run now" work), and Contents to Read and write (needed to save likes -- see the Likes page). Skip Contents if you only ever plan to view likes, never save one, from this device.
  4. Click Generate token and copy it — GitHub only shows it once.

Genres

Whole-word match against each record's genres and styles. "house" catches Deep House, not the other way round.

Formats

Kept if a listing matches ANY checked format. Nothing checked = keep every format.

Stores

The username is the store's Discogs seller name, from discogs.com/seller/<username>/profile — often different from their website. Click Check to confirm it exists and has items for sale. Leave Genres blank to use the global genre filter above for that store; fill it in to use different terms for just that one store instead (not in addition to).

Advanced timing

Raise both to see everything a busy store lists, not just the newest few hundred. A run can then take much longer (up to the workflow's timeout) - that's expected, and free either way.
